## `app/models/region.py`

Defines the `Region` model — the SQLAlchemy class representing the
`regions` table. This is the first table in Group 1 (Users & Auth) to
get a real model, since `users.region_id` will need `regions` to exist
first as a foreign key target.

### What it does
- Maps directly to the `regions` table: `region_id`, `region_name`,
  `region_code`, `is_active`, `created_at`, `updated_at`.
- `region_id` is a Postgres-native UUID, auto-generated by Postgres
  itself via `gen_random_uuid()` — not something the app has to
  compute in Python.
- `region_code` is unique — no two regions can share a code like "RO3".
- `created_at`/`updated_at` are stamped by Postgres (`NOW()`), not by
  the app's own clock — keeps timestamps consistent even if the app
  server's clock is slightly off.

### Why it matters for the account-creation flow
Regions must be seeded/added *before* any user can be assigned one —
`users.region_id` is a foreign key pointing here, so a user's region
dropdown is only ever populated from existing rows in this table.
Nothing in the user-creation flow inserts a new region as a side
effect; adding a region is its own separate action.
